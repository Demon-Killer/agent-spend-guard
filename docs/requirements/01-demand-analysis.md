# 需求分析

## 问题

AI 编程工具会快速且不透明地消耗 API 预算。开发者通常会把 Codex、Claude Code、Cursor、Cline、RooCode、OpenCode 或自研 Agent 直接连接到 OpenAI、Anthropic、OpenRouter、Gemini 等模型服务。

一旦接入，用户往往缺少项目级成本可见性，也缺少运行时硬限制。

常见问题：

- Agent 进入循环，反复调用模型。
- 工具在失败后隐藏重试很多次。
- 多个项目共用同一个上游 API Key。
- 团队成员共用一个 key，无法按人或项目统计。
- 上游平台账单只显示账户总消费，不显示 repo、工具、项目维度。
- 用户通常在收到账单后才发现异常消耗。

## 目标用户

| 用户 | 痛点 |
| --- | --- |
| 个人开发者 | 想知道每次 AI 编程会话到底花了多少钱 |
| 独立开发者 | 多个项目共用 key，无法按项目统计成本 |
| 小型研发团队 | 需要按成员或项目归因 AI 成本 |
| AI Agent 重度用户 | 需要防止 Agent 循环调用的熔断机制 |
| 企业研发团队 | 需要内部限额、审计记录和私有化部署 |

## 现有替代方案

OpenRouter：

- 优点：模型聚合强，统一账单，接入体验好。
- 不足：不是专门面向 AI Coding 成本防火墙；默认是云平台，代码 prompt 经过第三方会增加信任成本。

LiteLLM：

- 优点：通用能力强，支持很多 provider，开源。
- 不足：偏基础设施，范围较大，不是围绕“防止 AI 编程烧钱”这个单点结果来产品化。

模型服务商账单：

- 优点：官方账单准确。
- 不足：通常是账户级，不够项目级；无法对单个 AI 编程工具做本地硬熔断。

## 需求判断

需求是真实的，因为 AI 编程使用量正在增长，用户已经开始感受到预算不确定性。

最强切入点不是“更便宜的 token”，而是：

> 防止 AI 编程 Agent 烧光你的 API 预算。

这个需求足够窄，适合 OPC；同时技术杠杆高，匹配后端工程师能力。
